# Shrinking old photos buys nearly two years

Dawnage does not need a new storage provider. It needs to **re-save a few hundred oversized early-2026 photos at a smaller size and delete about 270 abandoned files**. That takes the private `progress_photos` bucket from **0.93 GB to roughly 0.3 GB (0.24–0.33 GB)**, which is **20–23 months of headroom** on the Free plan's 1 GB at today's upload rate. The reason is simple: **two-thirds of the bytes sit in 249 files larger than 1 MiB**. Nearly all are raw camera originals uploaded before the app started compressing photos in April 2026. Re-saving them at the size the app has used since April keeps every photo, strips any hidden GPS location data, and uses about ten minutes of GitHub's free compute. Deleting inactive users' photos **frees nothing today**, because no photo owner has been inactive for 12 months. It belongs in the privacy policy, not the storage plan. Moving photos to Cloudflare R2 or Backblaze B2 would take **3.5–5 developer days** and move access control out of the database into new code, all to avoid a **$25/month** Pro bill that launch will require anyway. None of the destructive steps may start until a **photo backup to Backblaze B2** exists. The nightly job written this week (uncommitted) backs up the database only, and Supabase deletes are permanent. Time is short: at today's growth the bucket crosses 1 GB around the **end of January 2027**. If the photo backup and the first cleanup are not done by **15 January 2027**, upgrade to Pro first. Upgrade anyway on the day paying clients depend on the app, or when the cleaned bucket climbs back to **0.8 GB**.

## The plan: back up the photos, sweep, shrink, then stop the leak

The order matters because two of the steps destroy data and only a backup makes them reversible. Supabase states that "Deleting an object removes it permanently" ([Supabase: Delete objects](https://supabase.com/docs/guides/storage/management/delete-objects)). This bucket has object versioning switched off, with 0 archived versions, so there is no hidden undo ([live storage note](../research_notes/Free%20photo%20storage%20options/live_storage_scenarios.md)). Storage is billed as an **average over the billing cycle** ("744 GB-Hrs"), not the live size, so "reducing storage late in the cycle lowers the average only gradually" ([Supabase: Storage size](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size)). Cleanups therefore belong in the first days of a cycle. Every number below comes from read-only queries run on 28 November 2026 unless marked otherwise.

## Two-thirds of the bytes sit in 249 old camera originals

The bucket's problem is history, not the current app. Files uploaded from January to March 2026 are **22.7% of files but 70.4% of bytes**: 384 files and 654.3 MB. Since April, 1,311 files have added only 275.3 MB, averaging about 180–250 KB a file month by month ([live storage note](../research_notes/Free%20photo%20storage%20options/live_storage_scenarios.md)). The early files were raw camera uploads at 1.4–2.3 MB on average. Today both the mobile app and the web dashboard shrink each photo on the device to a 1200×1600 box at JPEG quality 0.75 before uploading ([media note](../research_notes/Dawnage%20backend%20architecture%202026/media_timeseries_health.md)).

The second problem is **orphans**. These are files that no database row points to any more. **285 orphans hold 145.9 MB (15.7% of the bucket)**, and they keep accumulating: 17–55 more appear every month. They are created because no code path deletes a photo when a client replaces or removes it, and because a failed or stale save leaves the fresh upload behind. Since June, orphans have been **16.0% of all uploaded bytes**. Every one of the 1,410 database references points at a real file, so nothing is dangling the other way ([live storage note](../research_notes/Free%20photo%20storage%20options/live_storage_scenarios.md)).

Three Supabase mechanics shape how the cleanup must run. First, **deletes must go through the Storage API**. Deleting rows with SQL "will not remove the object from the bucket and will result in the object being orphaned" ([Supabase: Delete objects](https://supabase.com/docs/guides/storage/management/delete-objects)). Since March 2026 a trigger blocks such deletes by default; this project has it ([Supabase blog, 2026-03-05](https://supabase.com/blog/supabase-storage-performance-security-reliability-updates)). Second, **going over the quota is an organisation-wide event**. After a grace period of undocumented length, which one community case put at about three weeks, Supabase can apply "a 402 status code for all API requests" to every project in the organisation. Restrictions lift only at the next billing cycle or on upgrade ([Supabase billing FAQ](https://supabase.com/docs/guides/platform/billing-faq); [GitHub discussion #40081](https://github.com/orgs/supabase/discussions/40081)). Third, **the docs never say whether "1 GB" means 10^9 or 2^30 bytes**, so this plan assumes the stricter 10^9 until the Usage page shows otherwise ([Supabase: Storage size](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size)). Supabase's own object-versioning feature (public alpha) would make things worse on Free, because old versions "count toward your storage size". Leave it off ([Supabase: Object versioning](https://supabase.com/docs/guides/storage/buckets/object-versioning)).

## Re-encoding in place keeps every photo and strips GPS

Re-encoding means opening each oversized photo, shrinking it to a **1600 px long edge**, and saving it back as a JPEG at quality 80. That is the same size the app has produced since April. The recommended job **overwrites each file at the same path with the same `.jpg`/`.jpeg` name**, so no database row, URL format or installed app has to change. The `sharp` library removes all metadata by default, "which includes EXIF-based orientation". The job therefore applies the orientation to the pixels first and then drops GPS and camera data along with everything else ([sharp output API](https://sharp.pixelplumbing.com/api-output/); [compression and retention note](../research_notes/Free%20photo%20storage%20options/compression_retention.md)). That privacy gain matters. The legacy originals were likely unstripped camera files, and whether they carry GPS was never checked, because checking requires reading the photos ([media note](../research_notes/Dawnage%20backend%20architecture%202026/media_timeseries_health.md)).

JPEG beats newer formats for this one-off batch because almost all of the saving, roughly 1.6 MB down to 0.2 MB per file, comes from shrinking the dimensions, not from the format. One vendor benchmark found WebP only **6–22% smaller** than mozjpeg at equal quality, and AVIF **18–37%** smaller ([Cleanor Labs, 2026-07-04](https://cleanor.app/blog/next-gen-image-formats-2026-avif-webp-jpeg-xl-benchmark); vendor source, SSIM metric only). Across the batch that is worth about 5–30 MiB. Getting it would mean a new file extension, which every installed app currently rejects as "Unrecognized photo reference", plus rewriting 1,394 stored URLs ([compression and retention note](../research_notes/Free%20photo%20storage%20options/compression_retention.md)). JPEG XL is out entirely: Edge does not decode it ([caniuse](https://caniuse.com/jpegxl)), and Expo's image component does not list it ([expo-image SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/image/)).

The job runs as a **manually triggered GitHub Actions workflow**. A Supabase Edge Function cannot do it: functions get 2 seconds of CPU time, and Supabase lists `sharp` and `libvips` as unsupported ([Edge Function limits](https://supabase.com/docs/guides/functions/limits)). GitHub's free plan for private repos includes **$12 of compute a month at $0.006 per Linux minute**, about 2,000 minutes, and the batch needs about 10 ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). The job is a dry run unless told otherwise, **refuses to write until the operator confirms the B2 backup is verified**, skips any file whose new version is not at least 30% smaller, checks that each output has no EXIF data and a long edge of at most 1,600 px, and downloads every written file again to compare checksums. A full sketch of the script and workflow is in the [compression and retention note](../research_notes/Free%20photo%20storage%20options/compression_retention.md). Run it in four rounds: dry-run 20, apply 5, apply 100, then apply the rest. A second run does nothing, because every file is by then under the 500 KB threshold. The one HEIC file is an orphan, so the sweep removes it. The two referenced PNGs are small and can be left alone.

| Risk | Guard |
|---|---|
| Overwriting destroys the only copy of an original | The verified B2 mirror runs first. B2 keeps each replaced version **45 days**. Rollback is an rclone restore of the paths the job lists as `applied` |
| Visible quality loss on skin texture and muscle definition, which coaches compare | Quality 80, never below about 70. Compare 5 dry-run files side by side with the originals before approving |
| Colour shift when an iPhone colour profile is stripped | Unverified. Check one Display-P3 original in the dry run, and keep the profile if colours move |
| Viewers briefly see the old file | At most the existing 1-hour cache lifetime, and the old file looks the same. The mobile app does not cache photos at all |
| Download (egress) spike | ≈ **1.6 GB** in total: 0.93 GB for the first mirror, 0.53 GB for re-encode downloads and 0.08 GB for verification, against a 5 GB monthly allowance and ≈1.85 GB of normal monthly traffic. Do the mirror in this cycle and the re-encode in the next |
| The nightly mirror stops after the sweep | Its guard aborts any run that would delete more than 50 files. Override it once, deliberately, for the 268-file sweep |
| Running late in a billing cycle | Day 1–3 of a cycle captures nearly the full saving for that cycle. A day-25 cleanup captures about 20% |
| Leaked job key | Use a dedicated `sb_secret_` key and revoke it afterwards. The legacy `service_role` key retires at the end of December |

The figures in this table come from the [compression and retention note](../research_notes/Free%20photo%20storage%20options/compression_retention.md) and the [live storage note](../research_notes/Free%20photo%20storage%20options/live_storage_scenarios.md). The upload guidance is from [Supabase: Standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads).

**Future uploads need only small changes.** The most valuable one needs no app release. A single SQL statement limits the bucket to `image/jpeg` and `image/webp` at **2 MB**, so no client or direct API call can ever store a raw camera original, a HEIC file or an SVG again. Today the bucket accepts any image up to 20 MB ([media note](../research_notes/Dawnage%20backend%20architecture%202026/media_timeseries_health.md)). Six uploads since April were over 1 MB, which suggests an old web build still sends raw files, so check before locking. In the app, `manipulateAsync` is deprecated in SDK 57 and must be replaced with `ImageManipulator.manipulate(...).renderAsync()` anyway ([Expo ImageManipulator SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/imagemanipulator/)). The same change can switch the format to WebP at quality 0.8, but only if a test on about 20 real photos shows WebP at least **15% smaller on both iOS and Android**. At today's growth that gain is just 2–7 MiB a month. The web dashboard stays on JPEG, because Safari's canvas can silently return a PNG when asked for WebP ([WebKit bug 226950](https://bugs.webkit.org/show_bug.cgi?id=226950), 2021). Once in the stores, ship support for reading `.webp` one release before writing it, because older builds would show a blank photo ([compression and retention note](../research_notes/Free%20photo%20storage%20options/compression_retention.md)).

## Deleting inactive users' photos is privacy work, not storage work

The live data settles the storage question. **The 12- and 18-month inactivity rules catch nothing today.** All 153 users with any activity record were active on or after 25 December 2025, and Dawnage's data starts in December 2025. The only bytes such a rule touches are a single **256,730-byte orphan whose owner no longer exists**, and the orphan sweep removes that anyway. Shorter windows do catch bytes, but most of those bytes are the same legacy originals that re-encoding shrinks.

A **6-month** rule would delete the photos of **14–20 users**, holding 58.5–102.1 MB of referenced photos. After re-encoding, it adds only about **one month** of runway. A **3-month** rule would delete photos of 35–43 users for 2.8–3.6 extra months ([live storage note](../research_notes/Free%20photo%20storage%20options/live_storage_scenarios.md)). Package expiry is a poor stand-in for churn. **7 of the 12 clients whose package "ended" more than six months ago were active within six months.** Of 32 photo owners with no assigned coach, 20 were active within six months. Even when a 12-month rule starts to bite, around early 2027, the first group is **3 owners holding 11.5 MB** of referenced legacy photos.

**How "activity" is measured decides who gets deleted.** The app reuses a stored login session, and that does not update `last_sign_in_at`. A rule that relies on that field alone therefore overstates inactivity. Adding session refreshes and photo uploads removes 6 owners from the 6-month list and 8 from the 3-month list ([live storage note](../research_notes/Free%20photo%20storage%20options/live_storage_scenarios.md)). The retention job should use that broader signal. The n8n automation is now discontinued. Its 608 past writes to `daily_check_ins` were made with the service role, so some users may look more recently active than they were. That error delays deletion and never triggers it early, so it is safe. Going forward the signal gets cleaner.

The legal picture is consistent across Dawnage's four main client regions (India, the UK and EU, Canada, Australia). **Keep personal data only as long as it is needed, tell people the rule, and actually delete it, including from backups.** Body photos raise the stakes, because the ICO treats data revealing "health status" as special category data ([ICO: special category data](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/lawful-basis/special-category-data/what-is-special-category-data/)).

That points to a **12-month** rule. It is long enough for seasonal clients who pause and return, it satisfies India's one-year floor, and it is short enough to show photos are not hoarded (a lawyer should confirm). Photos are deleted after 12 months with no sign-in and nothing logged, **and** no active package, **and** no hold for a dispute or legal request. Emails go out **30 and 7 days** before, and signing in cancels the deletion. Only photos are removed; check-ins and measurements stay. There is no separate archive. The encrypted B2 backup keeps deleted photos for 30 days, which gives a best-effort restore window. Free email tiers easily cover fewer than 100 candidates a year: **Resend** allows 3,000 emails a month and 100 a day ([Resend pricing](https://resend.com/pricing)), and **Brevo** allows 300 a day ([Brevo help](https://help.brevo.com/hc/en-us/articles/208580669)). Both need a verified sending domain. The current privacy page, dated 22 November 2026, says only "We keep your data while your account is active." It needs replacing as soon as backups run, because even the database-only job keeps deleted accounts for 14 days. The proposed wording is:

> "Progress photos: if your account has had no activity for 12 months (you haven't signed in or logged anything) and you have no active coaching package, we delete your progress photos. We email you 30 days and 7 days before. Signing in before that date keeps them. Your check-ins, measurements and workouts are not affected."
>
> "Backups: deleted data, including photos, stays in our encrypted backups for up to 30 days and is then erased. If you come back within that time and ask us, we can try to restore deleted photos."

Source: [compression and retention note](../research_notes/Free%20photo%20storage%20options/compression_retention.md). After the cleanup is verified, set B2's 45-day setting back to 30, so the published "up to 30 days" stays true. Add "we resize it and remove hidden camera details, such as location" only after the re-encode and the EXIF test have shipped.

## A second free cloud dodges $25 a month at the cost of a week

Only three places offer permanent, commercially usable free storage suitable for private photos: **Cloudflare R2, Backblaze B2, and Supabase itself**.

**Cloudflare R2** gives **10 GB a month, free downloads**, 1 million writes and 10 million reads a month ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)). It has an Oceania location hint, which is "best effort" rather than guaranteed ([R2 data location](https://developers.cloudflare.com/r2/reference/data-location/)). Its docs require "an R2 subscription" through a checkout, which in practice means a payment card ([R2 get started](https://developers.cloudflare.com/r2/get-started/)).

**Backblaze B2** gives **10 GB free with no card**, and downloads are free up to three times the stored amount ([B2 pricing](https://www.backblaze.com/cloud-storage/pricing)). Its only regions are US West, US East, Amsterdam and Toronto; there is nothing in Asia-Pacific ([B2 regions](https://www.backblaze.com/docs/cloud-storage-data-regions)).

Everything else fails a basic test.

**A second free Supabase project adds capacity only in a separate organisation.** Quotas and Fair Use restrictions apply per organisation. The billing FAQ suggests a second Free organisation only to get around the project-count limit, and it also warns that "suspected abuse" can bring restrictions without notice ([Supabase billing FAQ](https://supabase.com/docs/guides/platform/billing-faq)). The overflow project cannot see Dawnage's logins, so it needs the same custom signing layer as R2, for one-tenth of R2's capacity ([free providers note](../research_notes/Free%20photo%20storage%20options/free_providers.md)).

The real cost of moving is not money but **who enforces privacy**. Today, database row-level security (RLS) decides who may open a photo: the owner, their assigned coach, or an admin. On R2, a new Edge Function would check each request and hand out time-limited links. R2 links work only on Cloudflare's own domain and cannot enforce a file-size limit the way Supabase does today ([R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)). A bug in that function is a data leak. The free providers note estimates **3.5–5 developer days**, covering the function and its tests, the mobile and web changes, account deletion, backups and migration. It also gives a sketch that reuses the existing `progress_photo_can_read()` check so the rules cannot drift ([free providers note](../research_notes/Free%20photo%20storage%20options/free_providers.md)). Hybrids are worse. Moving inactive users' photos to a "cold" store, or keeping thumbnails on Supabase and originals on R2, needs all of the R2 work plus routing logic between two vendors. And because growth comes from *active* users, a cold tier barely changes the curve. **R2 makes sense only if the owner refuses Pro after the cleaned bucket refills. B2 makes sense only if no card can be added.** Either way, B2's proper job here is to be the **encrypted backup**. Pro's own backups "do not include objects you store via the Storage API", so the photo backup is needed on any plan ([Supabase backups](https://supabase.com/docs/guides/platform/backups)).

## Pro becomes the right call at launch, or at 0.8 GB

Photo bytes are not what eventually forces the upgrade. Photo downloads run about **1.85 GB a month** today, extrapolated from a sample of less than one day. At about **400 users** they alone would exceed Free's 5 GB monthly allowance, and the realistic point for Pro is **about 300–500 users** ([media note](../research_notes/Dawnage%20backend%20architecture%202026/media_timeseries_health.md)). Before that, the trigger is a business one. Supabase's own advice is "If people rely on what you're building, even with light traffic, upgrade the project to a paid plan" ([Supabase KB](https://supabase.com/kb/faqs/platform/free-project-pausing)). Pro costs **$25 a month** and includes **100 GB of storage** and **250 GB + 250 GB of downloads** ([Supabase pricing](https://supabase.com/pricing)). That makes every free-cloud workaround redundant. Re-encoding is still worth doing on Pro, for GPS stripping and faster loading.

| Upgrade when… | Threshold |
|---|---|

Sources: [Free-plan note](../research_notes/free_plan_alternatives.md) §5–6 and the [Supabase billing FAQ](https://supabase.com/docs/guides/platform/billing-faq). The 15 January deadline is this report's own: the bucket's live size crosses 10^9 bytes about 2.1 months after 28 November. The 50–100-client scenario is roughly **four times today's per-uploader rate** of about 0.94 MB a month. That shows the real risk is launch engagement, not the photos already stored.

The case for upgrading **now** deserves a fair hearing. $300 a year removes the deadline, the grace-period risk and the pause risk at once. It does not remove the need for the B2 photo backup or the GPS strip. If the owner cannot give steps 3–6 a few focused days in December, buying Pro is the cheaper risk.

Two side effects of discontinuing n8n matter here. First, its daily writes no longer count as project activity, and Free projects pause after about seven days of low activity. The nightly database dump is real database traffic, but Supabase publishes no threshold and calls its heuristic no "guarantee" ([Supabase project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)). Adding one tiny API read to the nightly job closes that gap until launch traffic takes over. Second, nothing else now uses the database password, so resetting it to create the `SUPABASE_DB_URL` backup secret carries no risk of breaking another writer ([Free-plan note](../research_notes/free_plan_alternatives.md)).

## Conclusion

Dawnage's storage crisis is a leftover from three months, January to March 2026, before the app compressed photos. The pipeline since April is already lean. That changes the question from "where can we store more for free?" to "how do we undo one batch of old uploads safely?". The answer is the B2 photo backup. It gates every destructive step, Pro does not replace it, and it is the one prerequisite not yet built. Once it exists, shrinking and sweeping become reversible, supervised jobs that buy nearly two years at today's pace.

The deeper finding is that **today's stock of photos stops mattering once it is cleaned; what matters is photos per client per week after launch**. A hundred engaged clients would fill the cleaned bucket in about two months and push downloads past Free's limits soon after. Photo deletion should therefore be argued on privacy grounds, not storage. The $25 Pro decision should be tied to launch and engagement, not to the bucket size.
