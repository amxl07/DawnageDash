# iOS widgets and workout activity acceptance

The implementation uses `expo-widgets` 57.0.21 and `@expo/ui` 57.0.20 on Expo SDK 57. The Expo config plugin generates a real `ExpoWidgetsTarget` extension with two static WidgetKit kinds, `DawnageCheckIn` and `DawnageTraining`, and the SDK's `WidgetLiveActivity` registration. `DawnageWorkout` is an ActivityKit runtime factory, not a third shortcut widget. Push updates, frequent updates and Android widget generation are disabled.

Development, preview and production each have a separate extension bundle identifier and app group. For development these are `com.dawnage.app.dev.widgets` and `group.com.dawnage.app.dev`. Links derive from the installed build's configured scheme: `/daily-check-in`, `/plans` and `/logger`. All three destinations pass through the existing authenticated app gate. A signed-out open leads to sign-in/setup as appropriate; it does not bypass access checks or automatically submit anything.

Static snapshots contain only the variant URL and both theme palettes. They initialize at root startup, including signed-out startup. Launch a newly installed build once before adding its widgets. WidgetKit placeholder props may be empty; those layouts have safe labels and no assumed production URL. The system chooses the light/dark appearance and tinted/Lock Screen semantic rendering. Each supported size has exactly one root destination, with no misleading second tap target.

The workout payload contains only generic exercise index, exercise count, set counts and rest timestamps. Workout titles, exercise names, account IDs, dates, weights, reps, calories and other health values are excluded. Local account/run/lease ownership exists only in app memory. Explicit finish, save, discard, replacement and account changes end the activity. Normal navigation and saving a draft for later leave it owned by the session. Returning to editing from the finish review can explicitly resume an unsaved current workout. Past, saved and queued log editing cannot start a Live Activity.

Rest uses the provider's absolute `endsAt` or exact `pausedRemainingMs`; a separate memoized clock context avoids per-second ActivityKit writes. SwiftUI `Text(timerInterval:countsDown:)` continues while JS is suspended and clamps at zero. The native stale date is the rest deadline, or fifteen minutes after the last non-rest update. Every presentation switches to an honest open/refresh prompt when stale. This is a rest display, not a background alarm or guaranteed notification.

The single serialized writer coalesces edits, rejects stale leases, ends orphan instances before starting and reconciles on real foreground transitions. Failed cleanup retains ownership until end succeeds or native lookup verifies absence; retries are bounded per queued event. Only the focused logger claims/publishes a lease, and a retained logger reclaims it when focused again without ending the activity on blur. It contains missing-binary, Expo Go, old-OS and disabled-ActivityKit errors so workout editing and the in-app rest dock continue. User-dismissed native instances are not recreated on every foreground. A new run can try again. Android and web retain the in-app experience; these iOS surfaces are not advertised as available there.

## Native device checklist

Use a rebuilt iOS development/preview binary, iOS 16.4+ (the generated target minimum), and a signed app group/extension. Source tests, autolinking, prebuild and JavaScript export do not establish native device acceptance. A Mac with Xcode plus a simulator/device and signing access is required for these steps.

1. Install development and preview together. Launch each signed out. Add Check-in and Training in small Home Screen, circular, rectangular and inline Lock Screen sizes. Each opens its own installed variant and expected authenticated destination. Confirm gallery placeholders and first launch have no missing-layout error after startup initialization.
2. Check light, dark, tinted Home Screen, empty gallery placeholders, Always-On reduced luminance and large text. Confirm no container-background adoption diagnostic appears for either small widget. Labels remain readable and one root tap target is consistent in every size. Remove/re-add a widget after a build update.
3. Sign in using fictional test accounts. Open today's unsaved workout and complete a set. Confirm generic exercise/set progress on Lock Screen and compact, minimal and expanded Dynamic Island presentations. Inspect the payload visually for absence of names, measurements and personal details.
4. Start a 90-second rest, background/lock the app, wait beyond the deadline. The countdown reaches zero without counting upward, and stale copy requests opening Dawnage. Reopen the app; the in-app timer reconciles once. Repeat while paused, extending rest, resuming and skipping.
5. Navigate out of the logger with its draft retained. Use the persistent rest dock to pause, extend and resume. The same activity changes; no duplicates appear and navigation does not announce workout completion. Cover a logger with a check-in, open another logger from the Live Activity, then return through the stack to the original retained logger and finish there. Its current progress and finish must control the activity; covered editors must not take ownership.
6. Explicitly finish, return to editing, save, discard and replace a session. Each ends its prior activity; only deliberate resumed/replacement work may create another. Open yesterday's log, a saved record and a queued record and verify no new activity starts.
7. Kill and relaunch during rest/workout. On cold startup the old orphan is removed before any resumed current workout starts. Sign out during a native update, then sign in as a different fictional account. No previous activity survives or reappears. Static shortcuts remain generic.
8. Disable Live Activities in iOS Settings, dismiss an activity manually, and run the app in Expo Go or an older development binary without ExpoWidgets. All logger controls, saving and rest remain usable. Manually dismissed activities stay dismissed on foreground. Re-enable and begin a fresh workout to verify a new native start.
9. Validate build/archive on the team's current Xcode version and run a real-device pass, including ActivityKit authorization and widget extension entitlement provisioning. Record these results separately from the root source/prebuild verification report.

This host's previously verified limitation is CommandLineTools without a full Xcode/iPhone SDK; no successful native build or device pass is claimed by this implementation. Root verification owns fresh full-suite, prebuild, autolinking, export and toolchain evidence.
