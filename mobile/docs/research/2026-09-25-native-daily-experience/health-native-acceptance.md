# Native health import acceptance

Task 5 adds a real read-only HealthKit / Health Connect integration behind a lazy native boundary. Source/API verification is separate from native compilation and device acceptance. No real account or health records were used in implementation tests. Keep this distinction when recording results.

## Dependency and generated-project checks

Pinned dependencies: `@kingstinct/react-native-healthkit@16.0.0`, `@react-native-healthkit/core@16.0.0`, `react-native-nitro-modules@0.37.1`, `react-native-health-connect@4.1.3`. The core package is direct to make native discovery explicit. There is no deprecated `expo-health-connect` dependency. Source signatures were checked against the downloaded published packages; native compilation remains required.

Generate in an isolated copy/worktree so existing native files and the active Metro server are preserved. For development, preview and production, verify the active scheme is respectively `dawnage-dev`, `dawnage-preview`, `dawnage` and package/bundle suffixes match. Check:

- iOS autolinking/pods include ReactNativeHealthkit, ReactNativeHealthkitCore and NitroModules. HealthKit entitlement is enabled. No background-delivery, clinical-records entitlement or Health write usage description. The read usage description explains review and coach sharing on check-in submission.
- Android RN autolinking includes HealthConnect. Expo autolinking includes `react-native-health-connect-expo`, which registers the permission delegate without patching MainActivity.
- Android manifest includes only health `READ_WEIGHT`, `READ_STEPS`, `READ_NUTRITION`, `READ_HYDRATION` permissions. No health write, background or special history permissions. Provider package visibility comes from the library manifest.
- MainActivity no longer owns `androidx.health.ACTION_SHOW_PERMISSIONS_RATIONALE`. Exported `.HealthAccessActivity` owns that action and is declared before `ViewPermissionUsageActivity`. The alias retains `android.permission.START_VIEW_PERMISSION_USAGE`, `android.intent.action.VIEW_PERMISSION_USAGE`, `android.intent.category.HEALTH_PERMISSIONS`, export state, and targets `.HealthAccessActivity`.
- Generated `HealthAccessActivity.kt` forwards ACTION_VIEW to `<active-scheme>://health-access`, uses CLEAR_TOP/SINGLE_TOP, then finishes. The public route is outside `(app)` authentication/setup gates.
- Generated `android/gradle.properties` sets `android.minSdkVersion` to at least 26 for Health Connect. The plugin takes the maximum of 26, existing explicit property values, and the installed React Native `gradle/libs.versions.toml` minimum. A newer framework minimum or higher explicit value must be preserved. The current RN catalog has minimum 24 and compile/target 36, so the expected generated minimum is 26; compile/target remain 36. An unreadable framework minimum fails prebuild clearly instead of guessing a lower value.
- Build the iOS app with a supported EAS/Xcode image and Android with its configured SDK. Peer compatibility and generated configuration are not proof of successful native compilation.

## Device journeys

Use purpose-made fictional health records and a test account. Do not capture personal health values in logs, screenshots, analytics or artifacts.

1. Expo Go and web: open the import entry. Read the explanation and attempt access. The message “Health import is unavailable in this version of Dawnage. Continue entering values manually.” appears without loading unavailable native modules. A custom binary missing the module gives the same unavailable-version state, never a denied-permission claim or an unlock/access retry. For developer verification, rebuild/install the appropriate Dawnage native client after adding the pinned packages; Expo Go cannot add their native modules. Also test an HC package import that succeeds but its first native accessor throws the package linking error. Genuine provider and permission failures must retain their retryable error path.
2. Android unavailable provider, update-required provider, initialization failure: show the distinct recovery text; manual check-in stays usable. Test on an Android 13 device with the provider and an Android 14+ device with system Health Connect.
3. Permission entry is explicit: opening review does not prompt or query. Only “Choose access and read this day” begins authorization. Requests contain only seven HealthKit identifiers / four HC read record types, no writes. Double taps and close/reopen while the system dialog is pending must not overlap native permission requests.
4. iOS deny all: a completed permission dialog never means read access was granted. Reads may be empty; wording must explain no records or read access off/limited. Test partial/limited-date access as supported by the OS. Unlock/retry a locked-device error; no error becomes zero.
5. Android deny all and partial grants: denied types are not queried. Accessible types remain reviewable. Toggle/revoke access while review is open and retry. Historical dates outside permitted history remain unavailable/empty/error with manual entry available.
6. Empty records stay unanswered. A calories-only HC meal must never imply protein, carbs or fat zero: HC 4.1.3 serializes missing nutrition as zero. All ambiguous zero nutrition totals are omitted, even with origins. Enter a genuine zero nutrient manually. A zero step/hydration aggregate additionally requires a real raw record; explicit zero HK quantities remain valid.
7. Morning weight: records before midnight, at noon, after noon, invalid newest values and multiple morning samples. Pick the latest valid observation strictly before local noon in the selected day. Show its source and observation time. Do not average the day or relabel afternoon weight.
8. Units: kg, litres, dietary kcal and nutrient grams match the source apps at the check-in precision. In particular 1,250 mL is 1.25 L and 520 kcal is 520 kcal, not 520,000. Active/basal calories burned are not food intake.
9. Day bounds: yesterday/today, exactly midnight, a 23-hour DST day and a 25-hour DST day. Use local calendar next-midnight, with current day capped at read time. Today says “Today so far”. Historical totals still explain incomplete logging/access. Move timezone during a native request and before applying: old values must not be applied.
10. Steps: overlapping phone/watch/device records and cross-midnight activity. Compare platform aggregate totals with Apple Health and Health Connect. Never add overlapping raw steps or source totals in JS. iOS uses the single selected calendar bucket's combined sum; verify platform priority behavior on devices.
11. Form protection: type a complete number without blur, then open import. The committed value is the baseline and is not selected for replacement. Invalid/unfinished text keeps the review closed. Existing values display their current value and require selecting “Replace …”; empty fields alone default selected.
12. Apply is one editor update of selected valid fields. Unselected manual values, ratings, sleep, workout status and notes remain unchanged; all applicable required fields still validate. It never submits, writes to Health, or persists the review itself. After explicit apply, values use normal check-in draft persistence.
13. Change account/date/form/revision while a request is pending; close/cancel/unmount; return a late response; close and retry. No old response appears or writes into the new scope. A form change after results also blocks all application. Review cancellation leaves the original form intact.
14. Light/dark, large text, small phone, VoiceOver/TalkBack: all rows and footer are scrollable, checkbox label announces use/replacement and exact value/current entry, checked state is accurate, sources/date/time are available, controls meet minimum targets. Close returns focus to the import trigger. Reduced motion follows the shared sheet behavior.
15. Android privacy/rationale: from Health Connect permissions open the rationale link both cold and warm, signed out and signed in, on Android 13 and 14+. All variants open `/health-access`, not the authenticated home/sign-in/setup route. Confirm the text explains read-only access, explicit selection, submission to coach and revocation. Returning to a pending permission prompt must not discard or auto-apply data.

## Manifest composition regression

Expo's installed `withMod` executes the most recently registered Android manifest action before its intercepted predecessor. Merely listing the Dawnage plugin after Health Connect therefore does not make its normal `withAndroidManifest` action run afterward. The custom manifest wrapper now uses `withBaseMod` to await the intercepted chain before validating and retargeting HC's required alias. It retains the alias's exported state, permission, action and category, and removes the upstream rationale filter from MainActivity after that filter has actually been added.

The health config regression composes the installed `react-native-health-connect/app.plugin.js` and Dawnage plugin through Expo `withPlugins` / `compileModsAsync`. It starts with a temporary bare manifest containing only MainActivity, checks the serialized Activity/filter/alias and actual generated Kotlin file, repeats generation to assert byte-stable manifest output, and covers both registration orders. This regression requires neither an Android SDK nor changes to the app's live native directory; root's final source suite and isolated full prebuild still need to confirm the corrected source.

The same real mod pipeline now writes a temporary `android/gradle.properties` and resolves a project-local RN version-catalog fixture. Both plugin orders cover the required 26 floor, raising an explicit 24, preserving an explicit 29, adopting a future framework minimum 30, raising an older explicit 28 to that future minimum, and preserving an explicit 31 above it. Each case checks a single minimum property, unchanged compile/target 36 and unrelated settings, and byte-stable repeated properties output. Root owns execution and isolated prebuild inspection of the corrected source; no Gradle compilation result is implied.
