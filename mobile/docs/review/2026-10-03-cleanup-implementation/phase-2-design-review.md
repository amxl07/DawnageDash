# Phase 2 storage design review

Bounded source review, 2026-10-03. No app edits or tests. Findings refer to the source inspected during ongoing Phase 1 work.

## Required design fixes

1. **A record-level version is not answer provenance.** A legacy assessment becomes a mixed record as soon as its first revised section is saved with `__assessment_catalog_version: 2`. Retained legacy answers must not acquire revised labels or disappear because the record now selects the revised catalog. Keep flat JSON, but resolve historical labels by immutable question ID across the union of both catalogs. Treat the numeric version as writer/catalog metadata only. New IDs are required for changed meanings; never translate old essay answers automatically. If an unchanged ID has materially different instructions (notably q8), one record version cannot identify which instruction produced its retained value. The smallest option is to keep its historical definition for readback and make revised input guidance separate; otherwise use a new ID or explicit per-answer provenance. No general event-history system is needed.

2. **Specify readback classification independently of the version.** Both summaries currently iterate only `questionnaireSections`; simply replacing that export with active questions makes retired answers unreadable. Share a pure selector yielding relevant current answers and retained retired/hidden answers, with the correct catalog label for each ID. Preserve hidden drafts in storage and show them separately when their parent is No or unanswered. A newly introduced digestion parent is absent on legacy records: do not silently classify existing symptom ratings as current under an inferred Yes. Decide and document that legacy case. Metadata and unknown keys must survive saves without being rendered as questionnaire responses.

3. **Latest-read merge is necessary but does not alone prevent lost updates.** Mobile wizard `save` currently patches every question in the section, including unchanged q14/q33/q56/q64 values; this can overwrite a newer Profile edit read by `persist`. Web wizard sends its entire in-memory answers object, reads only `id`, and ignores that read error. Use changed-field patches against the acknowledged baseline, including explicit clears and retained hidden edits, on both clients. A read followed by replacement of text JSON still has a concurrent-write race; either add a conditional update against the original stored answers/progress and retry conflicts, or explicitly document that the design does not guarantee concurrent preservation. No production migration is needed to formulate that contract.

4. **Completion history and current validation need separate definitions.** Persisted completed section IDs may survive revision, but a user can clear a required answer in a completed section and Save draft; union-only completion retains that ID and may persist `completed`. Both summaries unconditionally announce completion, and Home reads only completed IDs. Define a shared current-validity calculation over visible active required fields, and how it affects status/readback while preserving stored completion history. Count deduplicated known IDs everywhere (Home already does; mobile wizard count does not deduplicate; web status uses raw array length). Do not globally reset legacy completion. Required-value checks must preserve valid zero ratings and reject whitespace-only required text.

5. **Web persistence and Profile compatibility are part of the necessary change.** Web `handleNext` advances and can announce completion after `saveProgress` catches a failure. Web fetch paths lack stale-account guards and complete state reset on missing rows. Web Profile ignores assessment read errors, uses `answer || profileFallback` (resurrecting explicit empty values), and writes all four overlap fields on any Profile save. Bring these consumers onto the shared parse/presence/patch rules; fail closed on read errors and advance only after acknowledged saves. Mobile Profile already preserves empty strings and checks the returned assessment row, but its sync patch also includes all four overlap fields. Keep q14/q56/q64/q33 stable and retain the existing policy that Profile does not create assessment rows.

## Smallest robust shared contract

Use the existing text JSON columns and stable section IDs. Export immutable definitions indexed by ID, active section selection, visibility, value-presence/validation, readback grouping, known-section completion counting, and a defined-only changed-field merge. Preserve unknown JSON keys as unknown values; a narrow `Record<string, string | number>` type does not describe preserved metadata or future values. Keep version metadata out of answer iteration and never downgrade an unknown future version on save. Both library entry points should re-export this contract; consumers should not duplicate visibility or history rules.

## Unverified questions for implementation

- The brief promises actual revised IDs and conditional mappings later; those are not yet specified, so the final reduction and all parent/follow-up semantics cannot be reviewed yet.
- Shared-module resolution for Metro, TypeScript, and the web build was not verified.
- The measurement protocol remains unverified; do not replace the ambiguous distance with an invented one. Historical readback also needs original units and scale anchors, which the mobile summary currently omits.
- Concurrent writes, account switching, conditional draft recovery, all ten section destinations, and acknowledged-save behavior need the planned implementation checks. No runtime claims are made by this review.
